# Solver investigation artifacts

See [the investigation report](../../../../docs/experiments/2026-10-01/go-server-solver-redesign-2026-10-01.md) for the retained implementation, results and limitations.

The baseline is the **starting uncommitted working tree**, including the earlier SIMD and CPU work. These patches are not patches against repository HEAD. Use separate disposable copies of the checkout; do not reverse the patch in a workspace containing later edits.

- `solver-2026-10-01-final.patch`: production source changes from that baseline. Generated fixtures are regenerated by `npm run test:go`; the PGO files are stored separately.
- `solver-2026-10-01-batch64.patch` and `solver-2026-10-01-batch32.patch`: corrected experimental independent-island batch implementations, applied to the starting baseline. They are amd64 SIMD prototypes, not production fallbacks. The float64 version includes its randomized scalar comparison. The float32 version changes arithmetic and has no retained TypeScript port.
- `solver-2026-10-01-same-rules-control.patch`: applies to the retained source and restores the old data structures while retaining the new convergence and rotation rules. Build it with `pre-solver-default.pgo`. This is a control for unchanged gameplay, not the original baseline.
- `solver-2026-10-01-velocity-audit.patch`: applies to the retained source. It forces all eight iterations while reservoir-sampling prepared constraints, then supplies a replay test. It is intentionally instrumented and must not be used for CPU timing.

Patches are in [patches/](patches/), measurements in [results/](results/),
and the shared PGO files in [Go CPU profiles](../go-cpu/profiles/).

## Build and measure

In a baseline copy, reverse the final source patch and select `benchmarking/experiments/2026-10-01/go-cpu/profiles/pre-solver-default.pgo`. In the retained copy, use `cmd/go-server/default.pgo`, also archived as `benchmarking/experiments/2026-10-01/go-cpu/profiles/solver-final.pgo`.

Build each test executable from its own source root:

```sh
GOCACHE=/tmp/unicorn-precision-go-cache GOEXPERIMENT=simd \
  go test -pgo=cmd/go-server/default.pgo -c -o /tmp/go-server-candidate ./internal/server
```

Keep the baseline at a different output path, then run from the retained checkout:

```sh
BEFORE_GOGC=800 AFTER_GOGC=800 GOMAXPROCS=2 CPU_AFFINITY=0,1 \
  REPETITIONS=5 TICKS=900 OUTCOME_COMPARISON=report \
  node benchmarking/tools/go-cpu-paired.mjs solver-repeat /tmp/go-server-baseline /tmp/go-server-candidate
```

Use `REPETITIONS=3 TICKS=3000` for the longer suite. Adapt affinity to the CPUs actually available. `report` is necessary for old versus new numerical rules; it does not validate client/server parity. Use the default strict mode for the same-rules control and PGO-only comparisons. Do not run builds, tests, profiling or other CPU-heavy work concurrently with timing.

The harness records user plus system CPU, outcomes, allocation data, runtime settings and executable hashes. The summary file uses sums of scenario medians; the harness's printed `x` values are speedup ratios, which are not percentages of CPU saved.

## Replay the precision audit

Apply the audit patch in a separate retained-source copy and build the server test executable there. For each of `convoy`, `spread`, `contact`, and `module`, run:

```sh
GOGC=800 GOMAXPROCS=2 SESSION_PLAYERS=32 SESSION_TICKS=3000 \
  SESSION_WORKLOAD=module SESSION_RESULT=/tmp/velocity-audit-module.json \
  /tmp/go-server-audit -test.run '^TestSessionBenchmark$'
```

The four result paths are consumed by:

```sh
GOCACHE=/tmp/unicorn-precision-go-cache GOEXPERIMENT=simd \
  go test ./internal/physics -run '^TestVelocityReplay$' -count=1 -v
```

Alternatively, decompress the four archived `solver-velocity-audit-*.json.gz` files into those `/tmp/velocity-audit-*.json` paths. The replay resets bodies and constraints for each solve. It compares the same input against eight iterations, reporting iteration fractions, absolute linear/angular errors and normalized error percentiles. Reservoirs are stratified by island kind, so unweighted reservoir averages are not whole-server speedup estimates.

## Interpret the earlier files carefully

The `solver-summary.json` and compressed raw files preserve the exploratory sequence, including unsuccessful and discarded checkpoints. Do not treat every recorded timing as a valid optimization:

- `solver-batch64-screen` precedes the corrected radius component; use `solver-batch64-fixed-screen`.
- `solver-bounds-screen` used a rejected AABB shortcut.
- Early separation/budget checkpoints precede the `Body.Advance` invalidation and two-frame motion-bound fixes.
- `solver-node-parity` is the failed platform-trig convergence experiment; it is not a passing parity report.
- `solver-table-node-parity` is the passing float32-table screen. `solver-final-node-parity` is the passing 3,000-tick float64-table suite.
- `solver-final`, `solver-final-long` and `solver-same-rules` precede only the last PGO refresh. `solver-pgo-refresh` isolates that refresh with strict unchanged outcomes. `solver-release` and `solver-release-long` include that profile refresh. `solver-retained` and `solver-retained-long` are the final source/profile confirmation after a cadence fallback guard for independently configured replication views.

The retained source is authoritative. Timing labels alone do not establish correctness, statistical confidence, or performance on Fly.io hardware.
